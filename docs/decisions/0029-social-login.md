# 0029. 회원제는 구글·카카오 로그인, 학번 연결은 샘물 로그인 성공으로

- 상태: 채택 (2026-11-16, 사용자 결정). [0011](0011-accounts-supabase.md)의 "학번 + 사이트 비밀번호" 가입을 대체한다. Supabase(서울)를 쓰는 것은 그대로다
- 관련: [0009](0009-data-minimization.md)(데이터 최소화), [0010](0010-abuse-limits.md)·[0013](0013-smul-failure-handling.md)(횟수 제한), 이슈 #58

## 맥락

기록은 학생 기기(localStorage)에만 있어 기기를 바꾸거나 브라우저 데이터를 지우면 사라진다(SPEC F10). 0011은 샘물로 재학생임을 확인한 뒤 학번 + 사이트 비밀번호로 가입하는 설계였다. 사용자는 구현 전에 다음 셋을 견주었다.

1. 자체 회원제 + 메일 2차 인증
2. 구글 로그인
3. 자체 회원제 안에서 구글 계정으로 한 번 더 인증

## 결정

- **로그인은 구글·카카오 두 가지만.** 자체 비밀번호·메일 2차 인증은 만들지 않는다.
- **학번 확인은 샘물이 한다.** 로그인한 상태에서 샘물 가져오기에 성공하면 그 계정을 그 학번에 연결한다. 학번만 넣어서는 연결되지 않는다.
- **학번 하나에 계정 하나, 계정 하나에 학번 하나.** 다른 계정이 같은 학번으로 샘물 로그인에 성공하면 연결이 그쪽으로 옮겨진다(나중에 성공한 쪽 우선). 진짜 학생은 샘물 비밀번호를 알기 때문에 다시 가져오면 바로 되찾는다.
- **저장은 학번에 붙인다.** 저장값(화면 상태 전체, JSON)은 학번 키에 두고, 연결된 계정만 읽고 쓴다. 연결이 옮겨지면 예전 계정은 바로 못 본다.
- **브라우저는 Supabase를 직접 부르지 않는다.** 로그인 시작·코드 교환·토큰 갱신·불러오기·저장·탈퇴를 모두 `/api/account`가 대신한다. 표는 RLS를 켜고 정책을 두지 않아(0010의 `smul_try`와 같음) 서버 함수(service role)만 쓴다. CSP `connect-src 'self'`를 그대로 둘 수 있다.
- **새 라이브러리 없이 PKCE**로 로그인한다. 브라우저가 code verifier를 만들고, Supabase Auth의 `authorize`(소셜 로그인)로 보낸 뒤 돌아온 `code`를 `/api/account`가 `token?grant_type=pkce`로 바꾼다.
- **연결 증명**: `/api/smul`이 성공하면 `HMAC(SMUL_KEY_SECRET, 'link:학번:만료시각')`(10분)을 돌려준다. 학생이 그때 로그인돼 있으면 바로, 아니면 로그인한 뒤 이 증명으로 연결한다. 10분이 지나면 샘물에서 다시 가져와야 한다.
- **탈퇴**하면 Supabase 사용자를 지우고, 연결·저장값은 외래 키 `on delete cascade`로 같이 지운다.
- 카카오는 회원번호만 쓴다. 이메일(`account_email`)은 받지 않고 Supabase 카카오 설정에서 **Allow users without an email**을 켠다.

## 근거

- **사용자 결정**(2026-11-16): "구글과 카카오 로그인 두 가지 방식으로 연결하자". 토스·카카오 본인확인은 쓰지 않는다.
- **공식 문서**: NIST SP 800-63B는 메일을 대역 외(out-of-band) 인증 수단으로 쓰지 말라고 한다. 메일 2차 인증은 보안 수준으로 쳐 주지 않는다.
- **공식 문서**: OWASP Authentication Cheat Sheet. 비밀번호를 직접 받으면 해시 저장·잠금·재설정 흐름을 모두 맞춰야 한다. 소셜 로그인은 그 부담과 털릴 거리(비밀번호 해시)를 없앤다. 2단계 인증·기기 확인은 구글·카카오가 한다.
- **공식 문서**: Supabase Auth는 Google·Kakao를 기본 제공 방식으로 지원하고 PKCE 흐름을 쓴다(supabase.com/docs/guides/auth/social-sign-in/auth-kakao, …/sessions/pkce-flow). 카카오 `account_email`은 비즈 앱만 받을 수 있고, 받지 않으면 "Allow users without an email"을 켜라고 안내한다.
- **사용자 결정**(대화): 본인 확인은 로그인 회사가 아니라 샘물이 한다. 남의 학번에 묶으려면 그 학생의 샘물 비밀번호가 필요하고, 그 비밀번호를 가진 사람은 이미 샘물에서 직접 성적을 볼 수 있으므로 새로 생기는 위험은 없다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 자체 회원제 + 메일 2차 인증(0011 확장) | 학생은 가입·비밀번호·메일 확인을 거쳐야 한다. 메일 코드는 피싱에 약하고, 비밀번호 해시가 우리 DB에 쌓인다. 기각 |
| 자체 회원제 + 구글 인증 | 실제 보안은 구글에서 나오고 우리 비밀번호는 털릴 거리만 늘린다. 학생은 두 번 일한다. 기각 |
| 구글 하나만 | 국내 학생은 카카오가 늘 로그인돼 있어 더 편하다. 사용자 결정으로 둘 다 |
| 토스 인증·카카오 인증서(실명 본인확인) | 실명·생년월일·연락처를 받게 되고 사업자 계약·건당 비용이 드는 것으로 안다(구체 조건 확인 불가). 학번 확인은 샘물이 이미 한다. 기각 |
| supabase-js로 브라우저에서 직접 | 새 의존성(0006 승인 필요), CSP에 Supabase 주소 추가, 공개 키 노출. 직접 REST로 30줄 남짓이면 된다. 미채택 |
| 연결 없이 계정마다 저장 | 남의 기록을 자기 계정에 올려 둘 수 있다. 학번에 붙이고 샘물로 연결하는 쪽이 본인 확인과 맞는다. 미채택 |

## 결과·한계

- **사용자가 할 일(코드 밖)**: Google Cloud 콘솔 OAuth 클라이언트, Kakao Developers 앱(REST API 키·Client Secret·동의 항목 `profile_nickname`만), Supabase Authentication → Providers에서 Google·Kakao 켜기, URL Configuration의 Redirect URLs에 운영 주소와 `http://localhost:5173/` 추가. 비밀값은 Supabase 대시보드에만 넣는다.
- 구글 로그인은 Supabase `auth.users`에 이메일을 남긴다. 개인정보 처리방침(이용안내)에 보관 항목(로그인 계정 식별값·이메일(구글)·저장한 정보), 보관 위치(서울), 탈퇴 시 삭제를 적는다.
- 저장은 마지막에 쓴 쪽이 이긴다(기기 둘에서 동시에 고치면 늦게 저장한 값이 남는다). 학생 한 명이 쓰는 서비스라 충돌 합치기는 만들지 않는다.
- 토큰(refresh)은 localStorage에 둔다. supabase-js 기본값과 같다. XSS가 나면 털릴 수 있으므로 CSP(`script-src 'self'`)를 유지한다.
- **확인 불가**: 카카오 동의 항목에서 `account_email`을 뺀 앱으로 Supabase 기본 scope 요청이 통과하는지(문서는 된다고 함), 실제 로그인 왕복(사용자가 공급자 설정을 마친 뒤 확인).
