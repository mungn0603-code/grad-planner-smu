# 0010. 서버 중계 로그인 남용 방어: 시도 횟수 제한

- 상태: 채택 (2026-10-21). 같은 날 레퍼런스 조사 뒤 2차 보강(서비스 전체 차단기, IP 하루 실패 상한)을 채택했다(아래 '2차 보강'). **일부 대체됨(→ [0013](0013-smul-failure-handling.md))**: 차단기 집계 범위(시스템 장애만)·줄임 단계·반쯤 열림, IP 하루 실패 100회 → 최근 24시간 50회, 학번 1시간 3회 → 한 번에 하나 + 점진적 대기. 아래 기록은 당시 결정으로 그대로 둔다
- 관련: `api/smul.ts` `limit`, `supabase/migrations/20261021131227_smul_try.sql`, `src/smul.test.ts`, [`docs/handoff/2026-10-21-smul-security.md`](../handoff/2026-10-21-smul-security.md), [`ARCHITECTURE.md` §6-5](../ARCHITECTURE.md)

## 맥락

자동 보안 검토(2026-10-21)가 `api/smul.ts`에 요청 횟수 제한이 없다는 점을 중간 위험으로 지적했다. 서버 중계(0008)라서 생기는 위험 세 가지:

1. **대입 창구**: 응답이 401(비밀번호 오류)·423(잠김)·200을 구분해 준다. 남의 학번으로 비밀번호를 대입하는 도구가 될 수 있다.
2. **학교 쪽 차단**: 모든 요청이 서버 IP에서 나간다. 샘물은 매크로를 실시간 적발해 IP를 차단한다고 공지한다. 남용 한 번에 모든 학생의 가져오기가 막힌다.
3. **계정 잠금 유발**: 샘물은 로그인 5회 실패 시 계정을 잠근다. 남이 특정 학생을 잠글 수 있다.

## 결정

샘물에 요청하기 **전에** 횟수를 센다.

| 항목 | 값 | 이유 |
|---|---|---|
| IP 한도 | 1분 10회 | 한 곳에서 몰아치는 요청을 막는다. 같은 와이파이 학생들이 한 IP로 묶이는 점을 고려해 넉넉히 둠(사용자 결정, 처음 제안 10분 10회에서 변경) |
| 학번 한도 | 1시간 3회, 성공하면 초기화 | 샘물 잠금(5회) 전에 멈춰 우리 서비스만으로는 잠금까지 가지 못하게 한다. IP를 바꿔도 학번으로 센다 |
| 세는 시점 | 샘물 요청 전, DB에서 원자적으로 +1 | 실패 뒤에 세면 동시에 10개를 보냈을 때 10개가 모두 통과한다. 먼저 올리면 3개만 통과한다 |
| 순서 | IP 먼저, 통과하면 학번 | IP에서 막힌 요청이 학번 횟수를 올려 다른 학생을 막지 않게 |
| 키 | `HMAC-SHA256(SMUL_KEY_SECRET, 'ip:'+IP 또는 'id:'+학번)` | 학번은 9자리 숫자(10⁹가지)라 그냥 해시는 전부 대입해 되돌릴 수 있다. 서버 비밀값이 있어야 계산된다 |
| IP 출처 | `x-forwarded-for` 첫 값 | Vercel이 이 헤더를 덮어써 위조를 막는다(공식 문서) |
| IP 하루 로그인 실패 | 100회(2차 보강) | 아래 '2차 보강' |
| 서비스 전체 | 10분 실패율 50%·최소 20회면 모든 중계를 멈춤(2차 보강) | 아래 '2차 보강' |
| 저장소 | Supabase 표 `smul_try(k, n, until)` + RPC `smul_try`·`smul_ok`, 읽기는 표 직접 조회 | 2단계 회원제(0011)에 쓸 Supabase가 이미 있어 새 저장소·의존성이 필요 없다. RLS를 켜고 정책을 두지 않으며 실행 권한은 service_role만 |
| 장애 시 | 저장소 오류·3초 초과·환경변수 누락이면 503(막음) | 학생 계정 잠금 방지를 가용성보다 먼저 둔다. 로컬 개발(환경변수 없음, `VERCEL` 없음)에서만 건너뜀 |

## 근거

- **측정(시험)**: 학번 3회 뒤 4회째는 IP를 바꿔도 429이고 샘물로 나가지 않는다. 성공하면 학번 기록이 지워진다. 같은 IP 11회째는 429. 저장소 오류·Vercel 설정 누락이면 503이고 샘물로 나가지 않는다. 요청 본문·주소에 학번·IP 원문이 없다. 2차 보강: 전체 실패율 45%는 통과·50%는 503, IP 하루 실패 100회면 그 IP만 429, 로그인 실패(401)만 IP 하루 실패로 세고 성공은 실패로 세지 않는다(`src/smul.test.ts` 8개).
- **측정(실제 DB)**: Supabase에서 같은 키로 세 번 부르면 3, 기한이 지나면 1부터 다시 센다. 공개 키로 RPC·표를 부르면 401 `permission denied`. 보안 조언은 `rls_enabled_no_policy`(INFO, 의도한 것) 하나. 2차 보강의 표 읽기 주소(`k=in.(…)&until=gt.…`)는 실제 PostgREST가 문법 오류 없이 받는다(공개 키로 보내 400이 아니라 권한 거부 401이 오는 것으로 확인). service_role은 표 읽기 권한과 RLS 우회 권한이 있다(SQL 확인).
- **공식 문서**: Vercel `x-forwarded-for` 덮어쓰기, Supabase `apikey` 헤더만으로 service role 인증(새 `sb_secret_` 키·예전 키 모두).

## 2차 보강: 후보 비교와 채택 (2026-10-21)

1차 안(IP 1분·학번 1시간)을 레퍼런스와 비교하니 두 구멍이 보였다. ① 여러 IP로 나눈 공격은 IP·학번 제한을 모두 피해 샘물로 실패를 쏟아 낼 수 있다(위험 2). ② 학번마다 3회 미만으로 머물며 흔한 비밀번호를 여러 학번에 돌려 넣는 비밀번호 스프레이를 IP 1분 한도로는 하루 약 14,000회까지 허용한다. 학번은 순서대로 매겨져 짐작하기 쉽다.

| 후보 | 실제로 쓰는 곳 | 막는 위험 | 우리 상황에서의 비용·부작용 | 판단 |
|---|---|---|---|---|
| **P1. 서비스 전체 실패율 차단기** | 회로 차단기(circuit breaker) 패턴. Java 표준급 라이브러리 [Resilience4j](https://resilience4j.readme.io/docs/circuitbreaker)는 기본값으로 최근 호출의 실패율 50% 이상이면 열고(OPEN) 호출을 거절, 대기 후 시험 호출로 되돌린다. [Martin Fowler](https://martinfowler.com/bliki/CircuitBreaker.html)가 정리한 패턴으로, 외부 시스템 장애·과부하가 퍼지지 않게 하는 데 쓴다 | 2(학교의 서버 IP 차단). 공격자가 IP를 몇 개 쓰든 샘물로 나가는 실패 총량을 묶는다 | 코드 몇 줄, 같은 표, 새 의존성 없음. **부작용**: 공격자가 일부러 실패를 만들어 모든 학생을 최대 10분 막을 수 있다 | **채택**. 학교 IP 차단은 기간을 알 수 없고 모든 학생이 막힌다. 10분 멈춤이 훨씬 작은 피해다 |

| P3. 학번 한도를 상위 잠금의 절반 이하로(3 → 2) | [Microsoft Entra 스마트 잠금](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-password-smart-lockout): 앞단 잠금 임계값은 뒤쪽(온프레미스 AD) 임계값보다 **작아야** 하고, 뒤쪽이 앞단의 2~3배 이상이 되게 하라고 권한다. 우리 구조(앞단 = 학점플래너, 뒤쪽 = 샘물 5회 잠금)와 같다 | 3(계정 잠금) | 정상 학생이 오타 두 번이면 1시간 막힌다 | **보류**. 지금 3은 '앞단 < 뒤쪽' 조건은 지키지만 2배 권고(2.5 이하)에는 못 미친다. 다만 이 권고는 뒤쪽 실패 횟수가 시간이 지나면 초기화된다는 전제이고, 샘물이 그런지 확인 불가. 확인 뒤 다시 정한다 |

### 채택한 값과 이유

| 항목 | 값 | 이유 |
|---|---|---|
| 차단기 창 | 10분 고정 창 | 학번·IP 1분 한도보다 길게 보고, 멈춤도 최대 10분으로 짧게 |
| 차단기 조건 | 실패율 50% 이상 + 최소 20회 | 50%는 Resilience4j 기본값. 최소 호출 수는 Resilience4j 기본 100이지만 우리 이용량이 작아 20으로 낮췄다(정상 이용량 측정은 배포 전이라 확인 불가). 샘물 점검 시간(매일 12~13시, 18~19시)에도 실패가 늘어 멈출 수 있는데, 그때는 어차피 쓸 수 없다 |
| 무엇을 실패로 세나(차단기) | 샘물로 나간 호출 중 200이 아닌 모든 결과 | 회로 차단기는 오류·시간 초과를 모두 실패로 센다(샘물이 우리를 막기 시작한 신호일 수 있음) |
| IP 하루 실패 | 100회, 로그인 실패(401·423)만 | Auth0·rate-limiter-flexible 예시 값. 비밀번호 추측과 관계없는 샘물 장애로 학생 IP가 막히지 않게 |
| 키 | 전체는 `all:n`·`all:f`(개인정보 아님), IP 하루는 `HMAC('ipday:'+IP)` | 1차와 같은 원칙 |
| 검사 순서 | ① 전체·IP 하루(읽기 한 번) → ② IP 1분 → ③ 학번 → ④ 호출 수 +1 → 샘물 → ⑤ 결과 기록 | 이미 막힐 요청이 다른 횟수를 올리지 않게. 결과 기록 실패는 응답을 바꾸지 않는다 |
| 장애 시 | 1차와 같이 503 | |

**한계**: 차단기는 고정 창이라 호출 수 창과 실패 수 창이 조금 어긋난다(최소 20회 조건이 오탐을 막음). Resilience4j의 '반쯤 열림(시험 호출)' 단계는 두지 않고 창이 끝나면 닫힌다. 공격자가 일부러 차단기를 열 수 있다(위 부작용).

## 결과·한계

- 배포 때 Vercel 환경변수 `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`·`SMUL_KEY_SECRET`가 없으면 가져오기가 503으로 막힌다(의도된 동작).
- 실제 Vercel에서 헤더·Supabase 호출이 되는지는 배포 전이라 확인 불가.
- 샘물 실패 횟수가 시간이 지나도 쌓이는지 확인 불가. 쌓인다면 1시간 3회로도 천천히 잠글 수 있다.
- 근본 해결은 0008의 직접 로그인(앱) 또는 학교 API로 가는 것이다.
- 한 요청에 Supabase를 4~6번 부른다(읽기 1, 증가 2~3, 결과 기록 1~2). 같은 서울 리전이라 지연은 작을 것으로 보지만 측정은 배포 뒤.
