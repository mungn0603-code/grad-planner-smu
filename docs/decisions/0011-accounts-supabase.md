# 0011. 2단계 회원제·서버 저장은 Supabase(서울)

- 상태: 설계(미구현). 프로젝트 생성은 2026-10-21 사용자 승인, 현재 표는 `smul_try`(0010)뿐
- 관련: [`docs/superpowers/specs/2026-10-21-smu-cheonan-redesign-design.md` §4](../superpowers/specs/2026-10-21-smu-cheonan-redesign-design.md)

## 맥락

1단계는 수강 기록을 학생 기기(localStorage)에만 둔다. 기기를 바꾸거나 브라우저 데이터를 지우면 기록이 사라지고, 다른 기기에서 이어 쓸 수 없다. 사용자는 회원제 + 서버 저장을 결정했다(2026-10-21).

## 결정(설계)

- 백엔드는 Supabase 프로젝트 `credit-planner`(ref `chkmaephrtufzbktigfx`, 서울 ap-northeast-2, 무료 등급).
- 가입은 샘물 인증으로 재학생임을 확인한 뒤 학번 + 사이트 비밀번호로 만든다. 사이트 비밀번호는 Supabase 인증이 해시로 보관한다(최소 8자). 샘물 비밀번호는 저장하지 않는다(0009).
- 표: `students`(본인 행 읽기만, 쓰기는 서버 함수), `plans`(본인 행 읽기·쓰기). 행 수준 보안(RLS)으로 막는다.
- 서버 함수: `/api/join`, `/api/sync`, `/api/reset`(샘물 인증으로 사이트 비밀번호 재설정), `/api/quit`. 서비스 키는 Vercel 환경변수에만 둔다.
- `/api/reset`은 대입 표적이 되기 쉬우므로 0010의 횟수 제한을 처음부터 건다.

## 근거

- **사용자 결정**(2026-10-21): 회원제 + 서버 저장, 백엔드 Supabase.
- **확인**: 프로젝트 조회로 서울 리전(ap-northeast-2)·정상 상태를 확인했다. Postgres 행 수준 보안(RLS)과 인증(비밀번호 해시 보관)이 내장이라 별도 인증 서버가 필요 없다.
- 0010에서 같은 프로젝트를 횟수 제한 저장소로 써 보며 RLS·service_role 권한·RPC 호출을 실제로 확인했다.

## 벤치마킹

| 사례 | 내용 | 채택·미채택 |
|---|---|---|
| OWASP Credential Stuffing Prevention | 서로 다른 기기·IP에서 비밀번호 재설정이 반복되면 추가 확인 | `/api/reset`에 0010 제한 적용 |

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 기기 저장만 유지 | 기기 간 이어 쓰기 불가. 사용자 결정으로 기각 |
| 다른 백엔드(Firebase, 자체 서버+DB 등) | **기록 없음**: 결정 당시 비교를 저장소에 남기지 않았다. 구현 전에 이 칸을 채운다 |

## 결과·한계

- 가짜 이메일(`{학번}@{가짜 도메인}`)이 Supabase 이메일 검사를 통과하는지는 구현 때 확인한다.
- 구현 뒤 시험: 두 계정으로 다른 계정의 `plans`를 못 읽는지(RLS) SQL로 확인, Supabase 보안 조언 0건.
- 개인정보 처리방침에 서버 보관 항목·보관 위치(서울)·탈퇴 시 삭제를 적는다.
