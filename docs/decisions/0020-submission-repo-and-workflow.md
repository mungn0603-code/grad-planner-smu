# 0020. 제출용 새 공개 저장소로 파트별 이식, 브랜치·PR 규칙

- 상태: 채택 (2026-11-08 사용자 결정). 병합 후 브랜치 자동 삭제는 같은 날 대체됨(→ [0022](0022-branch-records.md))
- 관련: [`docs/SPEC.md`](../SPEC.md) '개발 규칙'·'이식 계획', `CLAUDE.md`, `.github/pull_request_template.md`

## 맥락

첫 버전(`mungn0603-code/grad-planner`, 비공개)은 커밋 35개가 모두 main에 직접 들어갔고, 한 커밋에 여러 변경을 긴 문단으로 적었다. 브랜치·PR·CI가 없었고, 작업 규칙과 "왜 이렇게 만들었는지"가 저장소 첫 화면에서 보이지 않았다.

2026-11-03에는 "새 저장소를 만들지 않고 기존 저장소에서 전환한다"고 정했다. 2026-11-08 사용자는 이 저장소를 개인 과제로 제출할 결과물로 보고, 새 저장소에서 엔진과 규칙을 한 파트씩 옮기며 처음부터 규칙대로 쌓기로 바꿨다.

## 결정

- 새 공개 저장소 `mungn0603-code/grad-planner-smu`를 만든다. 기존 저장소는 운영 중인 첫 버전으로 그대로 둔다.
- 브랜치: `main`(배포) · `dev`(기본) · 작업 브랜치(`feature/` `fix/` `refactor/` `docs/` `chore/` + 파트 번호).
- `main`·`dev` 보호: PR 필수(승인 수 0, 1인 개발), 관리자에게도 적용, 대화 해결 필수, 강제 푸시·삭제 금지. CI가 생기면(P1) 통과를 병합 조건에 더한다.
- PR은 merge commit으로 합친다. 한 커밋 한 변경으로 쌓은 이력을 그대로 남기려는 것이다. 병합된 작업 브랜치는 자동 삭제한다.
- Claude Code가 브랜치·커밋·푸시·PR·병합까지 대신 한다. 커밋 작성자는 사용자 한 명이고 AI 공동 작성자 표기는 넣지 않는다. 커밋·PR 문구는 사람이 한눈에 무엇이 바뀌었는지 알게 쓴다.

## 근거

- **사용자 결정**(2026-11-08): 새 저장소, 공개, 파트별 브랜치와 병합, AI가 병합까지 대신, 작성자는 사용자.
- **공식 문서**: GitHub 무료 요금제에서는 공개 저장소만 보호 브랜치를 쓸 수 있다([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). 그래서 공개로 했다.
- 승인 수를 1 이상으로 두면 작성자 본인은 승인할 수 없어 1인 저장소에서는 병합이 막힌다. 그래서 0으로 두고 "PR을 거친다"만 강제한다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 기존 저장소에서 전환(2026-11-03 결정) | 과거 이력(main 직접 반영, 긴 문단 커밋)이 그대로 남아 제출 이력으로 설명하기 어렵다. 사용자가 뒤집음 |
| 비공개 + GitHub Pro | 학생팩 Pro 여부를 확인하지 못했다. 공개로 무료 보호가 가능해 고르지 않음 |
| 보호 없이 규칙만 | 실수로 main에 직접 푸시해도 막히지 않는다 |
| squash 병합 | PR마다 커밋 하나로 줄어 "한 커밋 한 변경" 이력이 사라진다 |

## 결과·한계

- 공개 저장소이므로 비밀값·실제 학생 정보를 넣지 않는다. 테스트는 가짜 학생만 쓴다.
- 기존 운영 URL과 Vercel 프로젝트는 그대로다. 새 저장소 연결은 이식이 끝난 뒤 사용자가 한다.
- 승인 0이라 리뷰는 강제되지 않는다. 대신 PR 본문에 확인 방법을 적는다.
