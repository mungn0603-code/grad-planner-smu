# 0013. 샘물 연동 장애 대응: 실패 분류, 단계적 제한, 복구 확인

- 상태: 채택 (2026-10-21, 사용자 정책 지시). 0010의 일부(차단기 집계 범위, IP 하루 실패 100회, 학번 1시간 3회)를 대체한다. 0010의 나머지(IP 1분 10회, HMAC 키, 저장소, 장애 시 503)와 벤치마킹 기록은 그대로 둔다
- 관련: `api/smul.ts` `LIMIT`·`state`·`idDelay`·`check`·`record`, `src/smul.test.ts`, [`0010`](0010-abuse-limits.md), [`ARCHITECTURE.md` §6-5](../ARCHITECTURE.md)

## 맥락

0010 2차 보강의 차단기는 샘물로 나간 호출 중 200이 아닌 모든 결과를 실패로 셌다. 그래서 학생들이 비밀번호를 틀리기만 해도(401·423) 차단기가 열려 모든 학생이 최대 10분 막힐 수 있었고, 공격자가 틀린 비밀번호를 넣는 것만으로 서비스 전체를 멈출 수 있었다. 학번 1시간 3회는 남이 세 번 틀리면 그 학생이 1시간 막히는 구조였다. 사용자가 다음 정책을 정했다(2026-10-21).

1. 전체 차단기는 시스템 장애만 센다. 비밀번호 오류·계정 잠김은 세지 않는다.
2. 장애가 의심되면 요청 속도·동시 요청 수부터 줄이고, 심각할 때만 모두 멈춘다.
3. IP별 로그인 실패는 최근 24시간 50회, 그 IP만 막는다.
4. 같은 학번의 반복 실패는 점진적 지연과 짧은 쿨다운. 장시간·영구 잠금은 피한다.
5. 멈춘 뒤에는 대기 → 안전한 소수의 시험 요청 → 성공하면 단계적으로 재개.

## 결정

### 실패 분류(`Kind`)

| 분류 | 판정(현재 코드) | 전체 차단기 | IP·학번 실패 |
|---|---|---|---|
| `AUTH_REJECTED` | SSO 로그인 뒤 최종 주소가 로그인 화면 그대로 | 제외 | 셈 |
| `ACCOUNT_LOCKED` | SSO는 통과, 통합정보시스템 최종 주소가 `https://smul.smu.ac.kr/`가 아님(실제 잠긴 계정으로 **확인 불가**) | 제외 | 셈 |
| `UPSTREAM_TIMEOUT` | `TimeoutError`(요청마다 10초) | 셈 | 제외 |
| `UPSTREAM_CONNECTION_ERROR` | `TypeError` + `cause`(fetch의 DNS·연결 거부·끊김) | 셈 | 제외 |
| `UPSTREAM_SERVER_ERROR` | HTTP 5xx | 셈 | 제외 |
| `UPSTREAM_RATE_LIMITED` | HTTP 429 | 셈 + 곧바로 줄임 단계 | 제외 |
| `AUTHORIZATION_OR_ACCESS_BLOCK` | HTTP 401·403 | 제외, `all:blk`로 따로 셈 | 제외 |
| `UNKNOWN_UPSTREAM_ERROR` | 그 밖의 비 2xx(404 등), JSON 아님, `ERRMSGINFO`, 목록 모양 다름, 리다이렉트 초과 | 제외, `all:unk`로 따로 셈 | 제외 |

- 상태 코드만으로 원인을 확정하지 않는다: 5xx·429·401/403처럼 HTTP 의미가 분명한 것만 나누고 나머지는 UNKNOWN이다. 예전 '2xx 아니면 비밀번호 장기 미변경'은 근거가 없어 UNKNOWN(학생 문구: 샘물에 직접 로그인해 변경 안내를 확인하라)으로 바꿨다.
- `ERRMSGINFO`(HTTP 200 업무 오류)는 메뉴 권한 오류(§6-3에서 확인) 말고도 원인이 여럿일 수 있어 UNKNOWN이다. 샘물 문구는 그대로 학생에게 보인다.
- 실패는 `smul fail <분류> <상태>`로 로그에 남긴다(학번·IP 없음).

### 전체 차단기(상태 기계)

| 상태 | 들어가는 조건(10분 고정 창, 분모 = 성공 + SYS) | 하는 일 |
|---|---|---|
| 닫힘 | 아래에 해당 없음 | 그대로 |
| 줄임 | SYS 5회 이상·20% 이상, 또는 샘물 429가 1회라도, 또는 복구 뒤 10분 | 서비스 전체 1분 20회, 동시 2개 |
| 열림 | 호출 20회 이상·SYS 50% 이상 | 모두 503. 5분, 1시간 안에 다시 열리면 두 배(최대 10분) |
| 반쯤 열림 | 열림 대기가 끝남 | 한 번에 하나. 그 요청은 먼저 비밀번호 없는 시험 요청(`GET https://smul.smu.ac.kr/`, 2xx·3xx면 통과)을 보내고, 통과해야 학생 요청을 보낸다. 성공 2번이면 닫고 줄임 단계 10분. 시험 요청 실패나 SYS면 다시 열림 |

- 분자·분모 모두 SYS 기준: 비밀번호 오류·잠김·UNKNOWN·접근 거부는 분자에도 분모에도 넣지 않는다. Resilience4j `ignoreExceptions`("neither count as a failure nor success")와 같은 처리다.
- 관측 키에 창 번호를 붙여(`all:sys:<창>`) 분자·분모가 같은 창을 본다. 열 때 그 창의 관측을 지워, 닫은 뒤 옛 장애로 다시 열리지 않게 한다.
- 시험 요청은 학생 계정으로 로그인하지 않고 비밀번호를 다시 내지 않는다. 시험을 통과한 뒤의 학생 요청은 그 학생이 직접 누른 한 번뿐이다.
- 열림·반쯤 열림 상태는 표의 행(`brk:open`·`brk:half`·`brk:ramp`·`brk:trips`)이라 함수 인스턴스가 여러 개여도 같다.

### 재시도

서버는 샘물로 다시 보내지 않는다(로그인 재시도는 비밀번호를 한 번 더 내는 것이라 샘물 실패 횟수를 늘릴 수 있다). 화면도 자동 재시도가 없고 학생이 버튼을 다시 누른다. 그래서 지수형 대기·지터는 두지 않았다. AWS는 재시도가 과부하 때 부하를 키우므로 한 층에서만 재시도하고, 재시도한다면 상한 있는 지수형 대기와 지터를 쓰라고 권한다. 화면 자동 재시도를 넣게 되면 그때 지터를 함께 넣는다.

### IP

- 최근 24시간 로그인 실패(`AUTH_REJECTED`·`ACCOUNT_LOCKED`) 50회면 그 IP만 429. 1시간 칸 24개(`HMAC('ipf:'+IP):<시>`)를 한 번에 읽어 더하므로 '최근 24시간'은 1시간 단위로 근사한다. 성공은 세지 않는다. 49회 통과·50회 차단.
- 1분 10회(0010)는 그대로.
- `x-forwarded-for`는 `VERCEL` 환경에서만 믿는다(Vercel이 덮어씀, 공식 문서). 그 밖에서는 IP 제한을 건너뛴다(로컬 개발).

### 학번

- 한 학번은 한 번에 하나만 샘물로 나간다(`idl:` 자리, 60초 뒤 자동 만료). IP를 바꿔 동시에 보내도 하나만 간다.
- 로그인 실패 k번째 뒤 대기: ~~`min(30초 × 2^(k-1), 120초)`, k ≥ 3이면 15분~~ → 2026-11-10 사용자 결정으로 은행식으로 바꿈: 5번 실패마다 잠금, 1분 → 5분 → 10분 → 그 뒤 30분 고정(`LIMIT.id`). 샘물이 5회 실패에 계정을 잠그므로 우리 잠금이 걸리는 5번째 실패에서 샘물 계정이 먼저 잠길 수 있음을 알고 택했다(0010의 '샘물 5회 전에 멈춤' 원칙을 이 부분에서 내려놓음). 실패 수는 1일 보관, 성공하면 지운다. 시스템 장애는 학번 실패로 세지 않는다.
- 대기는 학번별 키라 다른 학번으로 번지지 않는다.

- **근거 약함(초기 후보)**: 줄임 단계 기준(SYS 5회·20%)과 한도(1분 20회·동시 2개), 열림 대기 5분·최대 10분, 반쯤 열림 성공 2회, 학번 대기 값은 레퍼런스 기본값이 아니라 우리 이용량을 짐작해 정한 값이다. Resilience4j 기본(최소 100회, 시험 10회)은 우리 이용량에 비해 커서 낮췄다. 실제 이용량·장애 빈도는 배포 전이라 확인 불가. 배포 뒤 `smul fail`·`smul breaker open` 로그로 다시 정한다. 값은 모두 `LIMIT` 한 곳에 있고 시험이 그 값을 읽는다.

## 결과·한계

- **샘물 계정 잠금 위험이 커졌다**: 남이 한 학번을 노리면 우리 서비스만으로 5번째 실패까지 약 31분(0·30초·1분30초·16분30초·31분30초)이 걸린다. 0010의 1시간 3회는 약 1시간이었다. 짧은 쿨다운(정책 4)과 맞바꾼 것이다. 샘물 실패 횟수가 시간이 지나면 초기화되는지는 여전히 확인 불가.
- **여러 IP로 나눈 비밀번호 스프레이**는 이제 차단기를 열지 않는다(정책 1). IP마다 1분 10회·하루 50회, 학번마다 대기로만 막는다. 학교가 이런 트래픽을 매크로로 보고 서버 IP를 막을 위험은 남는다. 보완 후보: 서비스 전체 로그인 실패량 상한(실패율이 아니라 양), 봇 확인(0010 P4).
- **공유 네트워크**: 학교 와이파이처럼 많은 학생이 한 IP를 쓰면 다 합쳐 24시간 50회 실패로 그 네트워크 전체가 막힌다. 실제 학교 와이파이가 IP 하나로 나가는지는 확인 불가.
- **시계**: 읽기는 함수 시계로, `smul_try`의 정리는 DB 시계로 만료를 본다. 대기·열림 키는 지운 뒤 새로 만들어 시계 차이로 옛 기한이 남지 않게 했다. 1분·창 경계는 몇 초 어긋날 수 있다.
- **비용**: 닫힘 상태에서 한 요청에 Supabase를 7~9번 부른다(읽기 2, IP 1분·학번 자리 2, 결과 기록·자리 놓기 3~5). 줄임·반쯤 열림에서는 2~3번 더. 지연은 배포 뒤 측정.
- **시험 요청의 의미**: 샘물 첫 화면이 2xx·3xx를 주는지는 실제 샘물로 확인 불가(가짜 샘물로만 시험). 첫 화면이 살아 있어도 로그인 서버가 죽어 있을 수 있어, 시험 뒤 학생 요청 결과도 함께 본다.
- 마이그레이션 변경 없음(기존 `smul_try`·`smul_ok`로 자리 잡기·삭제를 함). 배포·실제 DB 반영은 하지 않았다.
