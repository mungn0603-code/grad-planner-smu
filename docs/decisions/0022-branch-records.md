# 0022. 브랜치마다 이슈로 기록하고, 병합해도 브랜치를 남긴다

- 상태: 채택 (2026-11-08 사용자 결정)
- 관련: [0020](0020-submission-repo-and-workflow.md)(일부 대체), `CLAUDE.md` '브랜치와 PR', `.github/pull_request_template.md`, 이슈 #4~#8

## 맥락

0020은 작업 브랜치를 병합하면 자동으로 지우게 했다. 그러면 저장소에서 "어떤 브랜치가 무슨 기능을 했는지"는 PR 목록을 뒤져야 알 수 있고, 브랜치 목록에는 남지 않는다. 사용자는 브랜치별로 어떤 기능·작업인지 기록하면서 하고, 브랜치와 기록을 남기라고 했다(2026-11-08).

## 결정

- 브랜치를 따기 전에 **이슈를 먼저 만든다.** 본문은 `무엇을 / 왜 / 완료 기준 / 기록`이고, 기록에 브랜치 이름을 적는다.
- 작업 중 생긴 결정·측정 결과는 그 이슈에 **댓글로 쌓는다**(예: #7의 파트 경계 조정, 로컬 측정표).
- PR 본문 첫 줄에 `Closes #이슈`를 적어 이슈 · 브랜치 · PR을 잇는다.
- 병합해도 작업 브랜치를 **지우지 않는다.** 저장소의 자동 삭제를 끄고, 이미 지운 `docs/P0-spec`·`docs/P0-stack-decision`·`chore/P1-setup`은 각 PR의 마지막 커밋으로 되살렸다.
- 이미 끝난 파트는 닫힌 이슈로 기록을 채웠다(#4·#5·#6).
- 라벨: `feature`(기능·이식), `chore`(환경·CI), `refactor`(구조 변경), `documentation`(문서).

## 근거

- **사용자 결정**(2026-11-08): 브랜치별 기록, 브랜치 보존.
- GitHub은 PR이나 커밋 메시지에 `Closes #번호`가 있으면 기본 브랜치에 병합될 때 이슈를 닫는다([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). 이 저장소의 기본 브랜치는 `dev`라서 dev로의 PR 병합 때 닫힌다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 저장소 안 작업 일지 파일(예: `docs/worklog/P2.md`) | 코드와 함께 남지만, 브랜치·PR과 자동으로 이어지지 않고 병합 충돌이 생기기 쉽다 |
| PR 본문만으로 기록 | PR은 브랜치를 다 만든 뒤에 열리므로 "왜 시작했는지"와 중간 결정이 빠진다 |

## 결과·한계

- 브랜치 목록이 파트마다 늘어난다. 이름에 파트 번호가 있어 정렬해 볼 수 있다.
- 이슈·댓글은 GitHub에 있고 저장소 파일에는 없다. 저장소만 받은 사람은 `docs/SPEC.md` '이식 계획'과 ADR로 흐름을 본다.
